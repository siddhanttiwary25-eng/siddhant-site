Same bet?

Siddhant Tiwary · model jev-1.14.0 · code on GitHub
  1. What it does

    Decides whether a Polymarket market and a Kalshi market are the same bet, a variant (same race, different terms), or unrelated.

  2. How Jev is used

    One API call per pair. Jev reads both markets' full rules and returns a same / variant / different choice with probabilities, plus yes/no checks on subject, terms and deadline.

  3. The value

    Aggregators link markets without manual review, desks trust which spreads are real, and brokers never list two different bets as one. 0 false matches on 197 hard pairs, at $46 per million pairs.

Result: Jev made 0 false matches and found 34 of 37 true twins. Title matching at its best: 11 false matches, 22 missed.

Who buys this, and how I'd sell it

Jev tells you whether two markets are the same bet, a variant, or unrelated, with a calibrated probability, in under a quarter second, for about five cents per thousand pairs.

Ideal customers

Prediction-market aggregators and data APIs

They sell one view across Kalshi, Polymarket and others. Every new market has to be linked to its twin by hand or by brittle title rules.

Trigger
A new venue or a new category (sports, macro) doubles the matching backlog.
Buyer
CTO or head of data

Brokerages and sportsbooks adding event contracts

They list contracts from several exchanges and must avoid showing two listings as the same bet when the terms differ.

Trigger
Launching a prediction-market tab or adding a second venue.
Buyer
Head of product, event contracts

Market makers and arbitrage desks

Expanding coverage beyond a handful of hand-mapped markets.
Buyer
Head of trading or quant lead

Exchanges themselves

Objections

"We already use GPT or Claude for this."

Jev returns a structured choice plus probabilities, with no prompt parsing, at $0.042 per million input tokens and free output. The trial runs both side by side on your pairs, so the comparison uses your data, not ours.

"A wrong match costs us money."

Route by confidence. Act automatically only when Jev is confident; send the rest to a reviewer. The three yes/no checks (same subject, same terms, same deadline) tell the reviewer exactly why a pair failed.

"Our markets are different from your demo."

That is why the trial starts with 200 to 500 of your own pairs and a locked test set we agree on before running anything.

Trial playbook

Two-week proof of concept

The steps used here, packaged for any prospect's data. The repo is the starter kit.

  1. Day 0

    Kickoff

    Pick one workflow (listing dedup, arb leads, or catalog linking). Agree the success bar in writing, for example fewer than 2% false matches while catching 90% of true matches.

  2. Days 1-2

    Data

    Pull 200 to 500 candidate pairs from their catalog. Label them together, or use pairs they already mapped. Split into a dev set and a locked test set.

  3. Days 3-5

    Wire up

    Map their market fields into Jev's state. Start from this repo's question set. Tune instructions on the dev set only.

  4. Days 6-10

    Shadow run

    Run Jev next to their current method on live traffic. Log every disagreement and review it with their team.

  5. Days 11-14

    Readout

    Score the locked test set once. Report accuracy, false matches, missed matches, reviewer hours saved, and cost at their volume. Ask for the decision.

How this was built, and its limits
  • Data: every open Polymarket market (top 2,100 by volume) and Kalshi market (about 200,000) from public APIs.
  • Pairs: for each Polymarket market, the 2 Kalshi markets with the most similar titles; 200 sampled across similarity bands, 3 unclear dropped.
  • Labels: made with AI help from the full rules and reviewed by me. 10 corrected after Jev's first run flagged them (reasons in the repo). Scored against my original labels, before the fine-print corrections, tuned Jev still made 0 false matches and missed 13 of 47.
  • Tuning: first-draft instructions missed 30 twins. Rewritten on a separate 40-pair practice set with no shared markets, then the test set was run once.
  • 1096 input tokens per pair; this whole run cost $0.0091.
  • Not yet tested: a general-purpose LLM baseline and a larger labeled set.
